# execmon 단계별 테스트 시나리오

작성일: 2026-10-25
대상: **BTF, ring buffer, `bpf_get_current_task_btf()`를 지원하는 별도 Linux 실습 VM**
범위: 서버 생성·패키지 설치 단계는 이 문서의 범위에서 제외한다.

## 목표

`execmon`이 아래 흐름을 실제로 수행하는지 단계별로 확인한다.

```text
/usr/bin/id 실행
  → sys_enter_execve tracepoint
  → execmon.bpf.c가 이벤트 구조체 작성
  → ring buffer events map
  → execmon.c의 handle_event() callback
  → 터미널에 pid=... file=/usr/bin/id 출력
```

현재 프로그램은 **관찰 전용**이다. 프로세스를 종료하거나 네트워크를 차단하지 않는다. 모든 테스트는 운영 서버가 아닌 실습 VM에서만 한다.

## 진행 원칙

- 아래 날짜는 권장 순서다. 날짜가 바뀌어도 이전 단계의 성공 기준을 통과한 뒤 다음 단계로 진행한다.
- 실제 명령 출력, 커널 버전, 실패 로그는 해당 날짜의 `log/YYYY-MM-DD_진행_로그.md`에 남긴다.
- 오류가 나면 `error/YYYY-MM-DD_주제.md`에 원문·원인·조치를 기록하고 다음 단계로 넘어가지 않는다.
- ring buffer 자체는 Linux 5.8부터지만, 현재 PPID 수집 코드의 `bpf_get_current_task_btf()` helper는 Linux 5.11부터다. 따라서 **현재 소스의 최소 기준은 Linux 5.11 이상**이다. 5.4 서버에서는 perf event array 기반 legacy 변형이 필요하다.

## 2026-10-25 — 실행 대상 적합성 확인

### 목표

컴파일 전에 **현재 VM이 이 코드의 전제 조건을 만족하는지** 확인한다. 이 단계는 서버 구성 작업이 아니라, 구성된 서버가 프로젝트와 맞는지 확인하는 테스트다.

### 핵심 개념

- **BTF(Binary Type Format)**: 커널 구조체의 타입 정보다. `BPF_CORE_READ()`가 현재 커널에서 필드 위치를 맞추는 CO-RE에 사용한다.
- **ring buffer**: 커널 eBPF 프로그램이 사용자 공간 loader로 이벤트를 넘기는 큐다.
- **tracepoint**: 커널이 안정적으로 공개한 이벤트 지점이다. 여기서는 `sys_enter_execve`를 사용한다.

### 실행

프로젝트 소스를 VM의 작업 경로로 복사하거나 clone한 뒤, `execmon` 디렉터리에서 실행한다.

```bash
uname -r
uname -m
test -r /sys/kernel/btf/vmlinux && echo 'BTF: available' || echo 'BTF: unavailable'
if sudo bpftool feature probe kernel | grep -Eqi 'map_type.*ringbuf|ringbuf'; then
  echo 'ring buffer: available'
else
  echo 'ring buffer: unavailable'
fi
if sudo bpftool feature probe kernel | grep -q 'bpf_get_current_task_btf'; then
  echo 'current task BTF helper: available'
else
  echo 'current task BTF helper: unavailable'
fi
test -r /sys/kernel/tracing/events/syscalls/sys_enter_execve/format && echo 'tracepoint: available' || echo 'tracepoint: unavailable'
clang --version
bpftool version
```

### 예상 결과

- `BTF: available`
- `ring buffer: available`
- `current task BTF helper: available`
- `tracepoint: available`
- CPU 아키텍처가 `x86_64` 또는 `aarch64`임을 확인할 수 있음

### 실패 시 확인

| 증상 | 의미 | 다음 조치 |
| --- | --- | --- |
| BTF unavailable | CO-RE용 `vmlinux.h` 생성 기준이 없음 | BTF가 있는 최신 실습 VM을 사용한다. |
| ring buffer unavailable | 현재 커널이 ring buffer를 지원하지 않음 | Linux 5.11 이상 VM으로 바꾸거나 legacy 구현으로 전환한다. |
| current task BTF helper unavailable | 현재 소스가 PPID를 읽는 데 필요한 helper가 없음 | Linux 5.11 이상 VM을 사용하거나 PPID 수집 방식을 별도로 설계한다. |
| tracepoint unavailable | 해당 커널에서 목표 hook을 쓸 수 없음 | `/sys/kernel/tracing/events/syscalls/`를 확인하고 환경을 재점검한다. |

### 기록할 내용

`log/2026-10-25_진행_로그.md`에 커널 버전, 아키텍처, 세 가지 available 결과를 기록한다.

## 2026-10-26 — BPF 객체와 skeleton 생성

### 목표

`execmon.bpf.c`를 커널용 BPF ELF 객체로 만들고, loader가 호출할 skeleton 헤더를 생성한다.

### 핵심 개념

- **BPF object(`.bpf.o`)**: 일반 Linux 실행 파일이 아니라 eBPF 명령어와 map 정의가 들어 있는 ELF 파일이다.
- **skeleton**: `bpftool`이 BPF object에서 생성하는 C 헤더다. loader가 map·프로그램·attach 함수를 타입에 맞게 호출하도록 돕는다.

### 실행

```bash
cd ~/execmon
mkdir -p build
bpftool btf dump file /sys/kernel/btf/vmlinux format c > src/vmlinux.h
clang -g -O2 -target bpf -D__TARGET_ARCH_x86 -Isrc -c src/execmon.bpf.c -o build/execmon.bpf.o
bpftool gen skeleton build/execmon.bpf.o > build/execmon.skel.h
file build/execmon.bpf.o
test -s src/vmlinux.h && echo 'vmlinux.h: created'
test -s build/execmon.skel.h && echo 'skeleton: created'
```

ARM64 VM이면 `-D__TARGET_ARCH_x86`을 `-D__TARGET_ARCH_arm64`로 바꾼다. `uname -m` 값이 `aarch64`여도 clang/libbpf 매크로 이름은 `arm64`다.

### 예상 결과

- `build/execmon.bpf.o`는 `ELF ... eBPF`와 유사한 설명으로 표시된다.
- `src/vmlinux.h`, `build/execmon.skel.h`가 비어 있지 않다.
- 이 단계에서는 아직 어떤 eBPF 프로그램도 커널에 attach되지 않는다.

### 실패 시 확인

| 증상 | 우선 확인할 항목 |
| --- | --- |
| `vmlinux.h` 생성 실패 | 10월 25일의 BTF 확인 결과와 bpftool 경로/권한 |
| `BPF_MAP_TYPE_RINGBUF` 미정의 | kernel UAPI header 또는 커널이 너무 오래된 경우 |
| `No available targets are compatible with triple "bpf"` | clang에 BPF backend가 포함되었는지 `clang --version` 확인 |
| skeleton 생성 실패 | 앞 단계의 `.bpf.o`가 생성되었는지, bpftool 버전 확인 |

커널을 바꿨다면 `src/vmlinux.h`를 반드시 다시 생성한다.

## 2026-10-27 — loader 빌드와 최소 기능 테스트

### 목표

사용자 공간 loader가 BPF object를 load·attach하고 ring buffer 이벤트를 화면에 출력하는지 확인한다.

### 핵심 개념

- **loader**: 일반 사용자 공간 C 프로그램이다. BPF object를 verifier에게 검사받아 커널에 load하고 tracepoint에 attach한다.
- **verifier**: eBPF 프로그램이 안전한 메모리 접근과 허용된 동작만 하는지 load 전에 검사하는 커널 검사기다.

### 실행

터미널 A에서 빌드하고 실행한다.

```bash
cd ~/execmon
cc -g -O2 -Wall -Ibuild -Isrc src/execmon.c -lbpf -lelf -lz -o build/execmon
file build/execmon
sudo ./build/execmon
```

터미널 A에는 아래 시작 메시지가 보인 채 실행 상태여야 한다.

```text
execmon started; press Ctrl-C to stop
```

터미널 B에서 인자를 포함하지 않는 단순 실행 세 건을 차례로 한다.

```bash
/usr/bin/id
/bin/echo hello
/usr/bin/true
```

### 예상 결과

터미널 A에는 다음 형식의 줄이 세 줄 이상 보인다. 실제 PID와 PPID는 VM마다 다르다.

```text
pid=1234     ppid=1200     uid=1000   comm=bash            file=/usr/bin/id
pid=1235     ppid=1200     uid=1000   comm=bash            file=/bin/echo
```

### 중요 관찰: `comm`은 왜 `id`가 아닐 수 있는가?

이 프로그램은 `sys_enter_execve`, 즉 `execve()` **진입 시점**에 읽는다. shell이 자식 프로세스를 만든 직후에는 그 자식의 실행 이미지가 아직 `id`로 바뀌기 전이므로 `comm`은 `bash`나 `sh`일 수 있다. 반면 `file`은 `execve()`에 전달한 대상 경로이므로 `/usr/bin/id`여야 한다.

따라서 이 단계의 핵심 성공 기준은 `file`이다. `comm`이 새 프로그램 이름과 다르다고 오류로 판단하지 않는다.

### 실패 시 확인

| 증상 | 우선 확인할 항목 |
| --- | --- |
| `failed to open and load` | root 권한, BTF, ring buffer 지원, verifier 로그 |
| `failed to attach` | tracepoint 존재 여부와 커널의 BPF 권한 정책 |
| 시작 메시지는 있으나 이벤트 없음 | 다른 터미널에서 실행했는지, 테스트 명령이 shell builtin이 아닌 절대 경로인지 확인 |
| `execmon.skel.h`를 못 찾음 | 10월 26일 skeleton 생성 결과와 `-Ibuild` 옵션 |

테스트 세 명령과 각각에 대응한 출력 줄을 저장한다. 명령행 인자·환경 변수는 로그에 기록하지 않는다.

## 2026-10-28 — 필드 검증과 정상 종료 확인

### 목표

수집한 PID, PPID, UID, 파일 경로가 현실과 맞는지 비교하고, Ctrl-C 종료 후 BPF link가 정리되는지 확인한다.

### 실행

터미널 A에서 `sudo ./build/execmon`을 실행한 상태로 두고, 터미널 B에서 실행한다.

```bash
echo "현재 shell: pid=$$ ppid=$PPID uid=$(id -u)"
/usr/bin/id
ps -o pid,ppid,uid,comm,args -p $$
```

이후 터미널 A에서 Ctrl-C를 한 번 입력한다. 종료 뒤 다음을 실행한다.

```bash
sudo bpftool link show
if sudo bpftool prog show | grep -Eq 'handle_execve|execmon'; then
  echo 'CHECK: execmon 관련 프로그램이 남아 있는지 상세 확인 필요'
else
  echo 'OK: execmon 이름의 프로그램은 보이지 않음'
fi
```

### 예상 결과

- 출력 이벤트의 `uid`는 `id -u` 값과 일치한다.
- 실행한 shell의 PID는 이벤트의 PPID 후보로 비교할 수 있다. shell 구현과 중간 프로세스에 따라 항상 완전히 같다고 단정하지 않는다.
- 종료 후 loader 프로세스가 사라지고, 해당 loader가 만든 BPF link가 남지 않아야 한다.

### 주의

`bpftool prog show`에는 시스템의 다른 BPF 프로그램도 함께 보일 수 있다. 이름만으로 전체 목록을 삭제하거나 unload하지 않는다. 이 시나리오에서는 **관찰만** 한다.

### 실패 시 확인

Ctrl-C 뒤 프로그램이 종료되지 않으면 signal handler 또는 `ring_buffer__poll()` 상태를 기록한다. BPF link가 남으면 `bpftool link show`와 `bpftool prog show`의 해당 줄을 오류 파일에 원문으로 남긴다. 임의로 detach나 삭제 명령을 실행하지 않는다.

## 2026-10-29 — 제한된 부하 관찰

### 목표

이벤트가 연속으로 발생할 때 loader의 출력과 CPU 사용량을 관찰한다. 이 테스트는 성능 보증이 아니라, 다음 개선점(드롭 카운터, 필터)의 근거를 얻는 단계다.

### 실행

터미널 A에서 이벤트 출력을 파일에 남긴다.

```bash
cd ~/execmon
sudo ./build/execmon > build/execmon-load.out 2> build/execmon-load.err
```

터미널 B에서 실행한다.

```bash
time for i in $(seq 1 1000); do /usr/bin/true; done
grep -c 'file=/usr/bin/true$' build/execmon-load.out
```

`pidstat`가 이미 설치되어 있다면, 별도 터미널에서 loader PID의 CPU와 메모리를 기록한다.

```bash
pgrep -a execmon
pidstat -p "$(pgrep -n execmon)" 1
```

부하가 끝나면 터미널 A에서 Ctrl-C로 종료한다.

### 예상 결과와 해석

- `build/execmon-load.out`에 `/usr/bin/true` 이벤트가 많이 쌓인다.
- 1,000과 정확히 같은 수가 나오지 않거나 시스템의 다른 이벤트가 섞일 수 있다.
- 현재 소스에는 ring buffer 예약 실패를 세는 드롭 카운터가 없다. 따라서 이 결과만으로 “드롭이 전혀 없다”고 결론 내리지 않는다.

### 실패 시 확인

| 증상 | 의미와 다음 조치 |
| --- | --- |
| 출력 수가 매우 적음 | loader 오류 파일, 커널 로그, stdout 기록 경로를 먼저 확인한다. |
| CPU가 과도하게 높음 | 출력·파일 기록 비용과 전체 이벤트량을 분리해 측정한다. 다음 구현에서 필터를 우선 검토한다. |
| 로그가 너무 빠르게 커짐 | 운영 배포를 진행하지 않는다. 로그 순환과 대상 필터가 필요한 상태다. |

## 2026-10-30 — 회고와 다음 구현 결정

### 목표

검증 결과를 사실과 추정으로 나누고, 기능을 한 번에 늘리지 않고 다음 한 가지를 고른다.

### 완료 기준 체크리스트

- [ ] `execmon.bpf.o`와 `execmon.skel.h`를 생성했다.
- [ ] loader를 빌드했다.
- [ ] `/usr/bin/id`의 `file=/usr/bin/id` 이벤트를 확인했다.
- [ ] `comm`이 실행 전 프로세스 이름일 수 있음을 실제 출력으로 확인했다.
- [ ] Ctrl-C 뒤 관련 BPF link 정리를 확인했다.
- [ ] 1,000회 제한 부하의 출력량과 관찰값을 기록했다.
- [ ] 민감한 `argv`와 `envp`를 수집하지 않았다.

### 다음 기능 후보 — 하나만 선택

1. **드롭 카운터 map 추가**: ring buffer 예약 실패 수를 수치로 확인한다. 운영성 측면에서 가장 먼저 권장한다.
2. **`sys_exit_execve` 추가**: 성공/실패와 return code를 연결한다.
3. **사용자 공간 필터**: 특정 UID 또는 파일 경로만 출력하도록 해 로그량을 줄인다.
4. **JSON Lines 출력**: JSON escaping·길이 제한을 먼저 설계한 뒤 추가한다.

추천 순서는 1번(드롭 카운터)이다. 현재 부하 결과의 신뢰도를 높이는 데 직접 필요하기 때문이다.
